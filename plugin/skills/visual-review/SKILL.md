---
name: visual-review
description: Visual review of a pull request by number, a commit range, or uncommitted work when given none — draws the Rust crates and modules, the web modules and the Rails layers and classes before and after the PR's merge base and head, `<from>..<to>`, or `HEAD` and the working tree, with added, removed and modified nodes and edges coloured, annotates it with Claude's notes and structural flags, serves it in the browser, and acts on the review the user sends back from the page. Use when the user runs /visual-review or asks to see what a PR, a range or their uncommitted work changed structurally.
argument-hint: [<pr number> | <from>..<to>]

# Visual review

Each `visual-review` below is shorthand for this command: run the command in full in its place, since nothing puts `visual-review` on `PATH`:

```sh
npx -y --prefix="$(mktemp -d)" --package="${VISUAL_REVIEW_PACKAGE:-@pablocm90/visual-review@0.18.0}" visual-review
```

The empty `--prefix` keeps the reviewed checkout's own `node_modules` and `.npmrc` from choosing what runs; the command still runs in the repo.

Range: `$ARGUMENTS`. With a PR number, the CLI fetches the PR and reviews it from its merge base to its head: run step 1 with the number in place of `'<range>'`, then use the data's `range` (a `<sha>..<sha>`) as the range from step 2 on, so the notes land on the page you read. In step 2 also read `gh pr view <n>` for the PR's title and description, as context for what each part is meant to do; the notes stay on structure and say nothing of the description itself.

With no argument, review the uncommitted work: the range is `HEAD..worktree`, run every `visual-review` below without `'<range>'`, and in step 2 read `git diff HEAD` plus each untracked file `git status --short` lists.

Run every command from the repository root (`git rev-parse --show-toplevel`, which is the worktree's root inside a worktree).

1. Run `visual-review '<range>'`. It takes a few seconds, longer the first time while npx fetches the package. On a non-zero exit, relay its stderr (for example `Unknown revision: <rev>`) and stop: no page was written. On success, stdout is exactly the page's absolute path, and the review data sits beside it with `.json` in place of `.html`. Done when it exits 0.
2. Read the review data and `git diff <from>..<to>`. The data's `diff.nodes` and `diff.edges` carry a `state`; every one that isn't `unchanged` is a touched part. A node with `renamedFrom` (its old path) or `formerLabel` (its old name) is one renamed node, not a removal and an addition: call it a rename. The data's `dangling` lists web calls whose path matches no route after the change; each one is a touched part on its calling file. The data's `readingOrder` holds `parts`, the changed parts (crates, modules, files, classes, or a box changed only outside them) in the order to read them, depended-upon first and removed ones after the rest, and `cycles`, each group of parts that depend on each other, read in id order; read the parts in that order. The data's `undrawn` holds the patches of changed files outside the graph (tools, plans, CI, config); read them too, for the summary. The data's `tests` lists each changed test file with every test in it, marked `added`, `removed`, `edited` or `unchanged`, or with `unreadable` and the parser's message in place of its tests, `stack`, the id of the stack it sits in, and `new: true` when the file didn't exist at the base. A removed test with `movedTo` and an added one with `movedFrom` are one test that moved between those files. The data's `symbols` lists each changed TS/JS file whose symbols were read, by `node` and `stack`: its `symbols`, each with a `name`, a `kind`, a `scope` when something holds it, `exported` on each side, and a `change` (`added`, `removed`, `edited`, `renamed`, `moved`, `formatting` or `unchanged`), with both sides' `signature` when it changed, `logic` on an edited or renamed function whose decisions changed (each line a `change`, `same`, `added`, `removed` or `changed`, a decision `kind`, its `base` and `head` text, a `depth` and a `line`, the head's unless removed), `renamedFrom` (and `probably: true` when only the bodies were alike) and `movedTo` or `movedFrom` (a node id); the export names it `added` and `removed`; and its `kind`, `api`, `logic` or `formatting`. A file that wouldn't parse has `unreadable`, the parser's message, in their place. `parsers` names the parser packages and their versions. The data's `metrics` holds, per changed node and its neighbours, each side's churn and, for a measured file, its lines, functions, cyclomatic and ABC; `findings` lists what the review raised, each with a stable `id`, a `dimension`, a `level` (`look` or `info`), a one-line `title`, and a `target` node or edge id and a `detail` when it has them: the head's crossings of `thresholds` (the cuts the review used, dimension `metrics`, churn counting commits over the `churnDays` before each side), the stacks not read, the changed files outside the graph, the calls with no route, the exported symbols changed (dimension `api`), the guards and catches removed and other decision changes (dimension `logic`), the files whose logic changed with no test changed alongside (dimension `tests`) and the files or stacks whose symbols weren't read. Cite them in a note where they explain the change. The data's `sinceReview`, there on a PR's later round, when a review sent from an earlier page sits in `.reviews/`, holds the `head` that review was of and either its `verdict` and `changed`, the `nodes` and `edges` ids changed since among those the PR changes at that head or this one, counting only paths it changes at either (so a merge of the base branch counts only where it touches one of those paths), and `changed.dropped`, the `nodes` and `edges` ids it had added at that head and has since removed, which `diff` no longer holds, or, with nothing to compare, `gone: true` when that commit no longer resolves or `unreadable`, the message, when reading it failed. A part the PR has since restored is in `changed` with the state `unchanged` in `diff`: name it as reverted. Say in the summary what changed since, or that it can't be told and why. Done when you can say, for each touched part and each undrawn file, what it does in this change.
3. Write the notes beside the page as `<name>.notes.json` (the page's path with `.notes.json` in place of `.html`), in this shape:

   ```json
   {
     "version": 1,
     "summary": [{ "text": "http-adapter now calls application directly", "target": "rust/crate/http-adapter" }],
     "tests": "The new serve test pins /api/info; nothing pins the AppInfo module.",
     "notes": {
       "rust/crate/http-adapter": { "text": "Adds the /api/info route.", "flag": "layer skipped" },
       "web/file/App.tsx -> web/module/modules/AppInfo": { "text": "App reads app info through the module." }
     }
   }
   ```

   - `notes` are keyed by a crate's, module's or file's `id`, or by an edge's `<from> -> <to>` ids. A stack (`rust`, `web`) takes no note. Leave `notes` out when nothing drawn is touched.
   - A file inside a web module has its own id, such as `web/file/modules/AppInfo/api/app-info.ts`; its note shows once the module is expanded.
   - A Rust module has its own id inside its crate, such as `rust/mod/application/sign_up`, and so does the crate's root file (`rust/mod/application/lib.rs`, or `main.rs` for a binary); its note shows once the crate is expanded. Edges between modules are their `use` lines.
   - A Rails class has its own id, keyed by its constant, such as `shop/class/Admin::UsersController`, inside its layer (`shop/layer/controllers`); its note shows once the layer is expanded.
   - Each note says what that part does in the change, in one or two sentences.
   - `summary` holds two to five items on the change's shape as a whole, undrawn files included. Give an item a `target` when it is about one node or edge.
   - `tests` is one or two sentences on the tests as a whole: what the listed tests pin, and what the change leaves untested, such as a modified part with no test change under it. When no test changed, say what that leaves unpinned. It heads the Tests tab.
   - Set `flag` to a short label only for a structural concern the graph shows: a new dependency direction, a layer reaching past its neighbour, a cycle, or coupling across the stack edge. The page shows it as a finding that needs a look. Give the note a `dimension` when another one in `notes.schema.json` fits the concern better, such as `dependencies` for coupling across the stack edge; left out, it is `structure`.
   - Keep to structure. Line-level findings belong to `/code-review`.

   Done when every touched crate, module, root file, Rails layer and class, and every added or removed edge between them as drawn with modules collapsed, has a note. A note on a file import counts for the module edge it is drawn into.
4. Run `visual-review '<range>' --notes '<notes file>'`. It fills the notes into the page from step 1 without reading the range again. A non-zero exit names the notes file and either the contract error or one line per problem (`unknown id <id>`, `no note on <id>`): fix the file and rerun. Done when it exits 0.
5. Run `visual-review serve '<page path>'` in the background, so you are told when it exits. It opens the page in the browser and prints `Serving <url>` on stderr. Done when that line is out, or when it has exited: then go to step 7.
6. Reply with the page's URL and path and the flags you raised, one line each, or "no flags", and say that a review sent from the page's **Review** panel comes back to you.
7. When `serve` exits, act on how it ended:
   - Exit 0 with a path on stdout: the user sent a review, written at that path. Read it: `verdict` is `approve`, `comment` or `request-changes`, `body`, when present, is the user's general comment on the whole change, and `comments` lists the user's comments and their answers to findings. A comment has an `anchor`, a `kind` and its `text`. The anchor says what it is on: `{ kind: 'part', id }` for a node or `{ kind: 'edge', id }` for an edge (`<from> -> <to>`), with the ids your notes use; `{ kind: 'symbol', id: '<file node id>#<scope.name>' }` for a function, method or class in that file, with `#<n>` after the id from the second symbol of that name there on (the first has none), as a getter and its setter are, counted in the order of that file's entry in the data's `symbols`; `{ kind: 'decision', id: '<symbol id>#<text>', text }` for one logic line of that function, its id built on the symbol's, `#<n>` included, quoting it, with `#<n>` after the id from the second line of that function reading the same on (a removed guard's or catch's id is its `logic:removed:` finding's id without that prefix); `{ kind: 'test', id: '<test file>#<heading › … › name>' }` for one test, with `#<n>` after the id from the second of those headings and that name in the file on (the first has none), counted in the order of that file's entry in the data's `tests`; or `{ kind: 'line', id: '<file>@<base|head>:<n>', text }` for a line of the diff, on the base side for a removed line, the head side otherwise, with the line's `text`: find the line by its text when the number has moved. Act on the narrowest thing the anchor names, not the whole file. A comment's `kind` says what it asks: `change` is a task on its anchor, `question` wants an answer, and `suggestion` is to be weighed: take it or say why not. An answer's anchor is `{ kind: 'finding', id }`, the `id` of one of the data's `findings`, or `notes:<id>` for the flag your note on `<id>` raised. Its `kind` says what it asks: `fix` is a task on what the finding names, `explain` wants an answer on why the change does that, and `fine` closes the finding, with the user's why as `text` when they gave one: name it in your reply with that why, and do nothing else for it. Take `body` first, as a comment on the whole change, under the same verdict. `read` lists the parts of the reading order the user marked read, and `reviewed` says what the page was drawn for, its `range` and, for a PR, its `pullRequest` number. A part in `read` with no comment on it was read and found fine: say nothing of it. In your reply, name the parts of `readingOrder.parts` that are neither in `read` nor commented on as not read, or say that no part was marked read when `read` is empty.
     - `request-changes`: do every `change` and `fix`, answer every `question` and `explain`, and take or turn down every `suggestion`, saying which, as you would a PR review's requested changes. Done when `body`, every comment and every answer are addressed or answered with why not.
     - `comment`: answer every `question`, `explain` and `body`, and for each `change`, `fix` and `suggestion` say how you would take it, naming its anchor; change nothing until the user says to. Done when `body`, every comment and every answer have a reply.
     - `approve`: answer `body`, every comment and every answer, if any, as under `comment`, then say the user approved and stop.
   - Exit 0 with nothing on stdout: the page was already served by an earlier `serve`, which receives its review. Say so and stop.
   - Exit 1: relay its stderr (`No review sent` when no tab opened the page within a day or none had it open for ten minutes since, or the user stopped it) and stop.
