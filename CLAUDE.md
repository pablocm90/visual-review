# visual-review

Structural review pages for pull requests, ranges and uncommitted work: the Rust crates and modules, the TS/JS modules and the Rails classes of a repo, before and after, with what changed coloured, and optional notes written by Claude or anyone else. Being made public as `@pablocm90/visual-review`.

## Where things are

The layout: `src/core/` holds the ports (`Reader`, `Linker`), config, `read-range.ts` and `read-stacks.ts`, the diff, the collapse rules (`visible-diff.ts`: what is drawn at an expansion, its unchanged edges merged per pair of boxes unless the page's "All edges" is ticked, and what going to an id opens) and notes, placed on them (`notes.ts`); the adapters sit behind the ports in `src/readers/{rust,typescript,rails}/` and `src/linkers/fetch-axum/`, listed in `src/adapters.ts`, which `cli.ts` hands to `readRange` (the core imports neither it nor `on-path.ts`); `src/git/` holds the git, `gh` and `PATH` plumbing; `src/viewer/` is the page, which imports the core and never the reverse. Bare file names below live in those folders.

- `src/cli.ts` is the entry point (`pnpm review <pr | from..to>`, or nothing for uncommitted work). `read-range.ts` checks out both sides of a range and reads each with `readStacks` (`read-stacks.ts`) through the readers in `src/readers/` (Rust: `crate-graph.ts`, `crate-modules.ts`, `rust-tests.ts`, `rust-measure.ts`; TS: `web-graph.ts` via dependency-cruiser, `typescript-tests.ts`, `typescript-measure.ts`; Rails: `rails-graph.ts`, `ruby-tests.ts`, `ruby-measure.ts`, parsing with tree-sitter-ruby in `ruby-syntax.ts`, no Ruby run), each implementing `Reader` (`reader.ts`): `roots` lists candidate roots, `holds` says whether one is its stack given that stack's settings, `graph` reads one stack under its drawn id, and it owns its test files, read only under a drawn root. `readStacks` owns the policy: naming, added and dropped stacks, labels, skips, linker stacks and edges with an undrawn end. It names roots in one pass, reader order then root order: a root's name (its own, else its directory, else the repo folder at `.`) gives a tentative id, the first free `~N` (`web~2`) when taken, and `holds` is asked with that id's settings; only a root that holds takes the id. A TS root is any directory with a `package.json` whose source root (tsconfig `rootDir`, else its one `include` folder, else `src/`) holds TS/JS sources, `node_modules` skipped; its stack id is the directory, or the package.json name (else the repo folder name) at the checkout root. A bare import of a sibling package's name joins the file to that stack, since checkouts have no `node_modules`. A Rails root is any folder with `config/application.rb` outside `vendor/`, `node_modules/`, `test/` and `spec/`, named by its directory, or the repo folder name at the checkout root; its boxes are the `app/` folders holding Ruby (`app/lib` as `app/lib`) plus `lib/`, or the deepest folder matching a config box glob (`app/models/*` gives `models/billing`; a box doesn't change a class's constant), and its nodes are classes keyed by constant (`<stack>/class/Admin::UsersController`), read from the file's `class`/`module` definition naming the longest tail of its path. Its edges are the constants a class writes, resolved through Ruby's lexical scope, and its model associations, resolved from the owner's constant as ActiveRecord does (`class_name:`, `source_type:`, `source:`, else the name, singularized for `has_many`, matched ignoring case). Its test files are `*_test.rb` under a `test/` folder and `*_spec.rb` under a `spec/` folder, read by one walker (`ruby-tests.ts`): `test "…"` calls and `test_` methods under a heading per class constant, and `it` / `specify` / `example` / `scenario` (an `it { … }` named by its block) and `it_behaves_like` (named by its arguments) under a heading per `describe` / `context` / `feature`, named as RSpec names groups; a test word on a receiver is no test, and shared and `x`/`f` groups aren't read. `config.ts` validates `visual-review.config.json` (Zod, `strictObject`), read from the head revision or else the working tree, and applies to both sides: readers get a stack's settings in `holds` and `graph` (box globs, `sourceRoot`), stacks added with `reader`+`root` keep their key as id, relabelling happens in `readStacks` on drawn ids, and a dropped (`false`) stack's graph is never read. A reader may name the command its `graph` runs (`Reader.tool`, `cargo` for Rust): when it isn't on `PATH` (`on-path.ts`, a lookup, nothing run), none of its stacks is read and the review lists its kept stacks as `skipped` (`skipped.ts`), shown on stderr and as the alert atop the page's findings rail; its test files are still read. The CLI looks up `git`, and `gh` for a PR number, the same way and exits 1 naming the one missing. Each `Reader` names itself and the stack fields it takes (`stackFields`). Naming problems (an added root detected as another stack, an added key detected elsewhere or drawn by another reader) fail before any graph is read; the rest (undetected, field not taken, unlinkable: `checkConfig`) once both sides are read. `pnpm build` writes `dist/config.schema.json` and `dist/notes.schema.json` from their Zod schemas (`write-schemas.ts`). Linkers (`Linker`, `linker.ts`) then draw edges across stacks from the drawn nodes: `linkers/fetch-axum/linker.ts` reads the fetch calls of every TS stack's files and the `.route("…")` paths in the module files (the files its targets reach, not `tests/` or nested crates) of every crate whose `Cargo.toml` depends on axum (`api-paths.ts` parses both), and lists unrouted calls as dangling; with no axum crate it draws nothing. The config's `linkers` entry turns one off or names its `from`/`to` stacks. `test-changes.ts` compares a test file's tests across the sides; each test file carries its stack's id (`stack`, from the deepest root of its reader holding it), since every reader draws its stack node at path `''`, which holds no path. `diff-graphs.ts` diffs the sides, matching edges by `edgeId` (`graph.ts`, the `<from> -> <to>` notes use too). `visible-diff.ts` draws a node inside closed boxes as the outermost of them, at any depth. `notes.ts` parses notes, places them at an expansion (an edge's note moves onto the edge drawn in its place) and lists their problems. `read-range.ts` also counts each side's churn per drawn file (`git log` over `metrics.churnDays` days before that side's committer date; uncommitted work's head counts up to `HEAD`), and `metrics.ts` puts it on the changed nodes plus one hop of the diff's edges, with fan-in/out and, from the reader's optional `measure` (Rust: `rust-measure.ts`; TS: `typescript-measure.ts` over Babel's AST; Rails: `ruby-measure.ts` over tree-sitter-ruby; TS and Rails test files measured as `undefined`, which leaves a file unmeasured), lines, functions, cyclomatic (its highest, its total and each function's, `cyclomatic.byFunction`) and ABC; a box takes the highest of each measured inside it (`highestInside`). `metric-findings.ts` raises the head side's leaves over the config's thresholds as `metricFindings`, `look` or `info`. `page.ts` is the page's contract: it builds the page data from a range reading (every field present, stamped with the CLI's version), puts data and notes into `viewer.html`'s slots and reads them back (`main.tsx` reads them through it, so it imports nothing from `node:`), and on `--notes` checks the notes against the data inside the page and refuses a page another version wrote. The CLI only does I/O around it; the `.json` beside the page is for readers such as the skill.
- `src/viewer/` is the page: React + ELK, built by vite with `vite-plugin-singlefile` into one file, `dist/viewer.html`. `review-page.tsx` holds the tabs (Structure and Tests shown so far, picked by the URL's hash; the selection is its state, so it holds across tabs) and the Structure screen: the findings rail on the left (`findings-rail.tsx`: skipped stacks, flagged notes, metric findings and what isn't drawn, each that acts going to its node or opening the changed files outside the graph), the graph, coloured by change, churn or complexity (`colour-by.tsx`), and the inspector on the right, its tabs Note, Metrics (`metrics-tab.tsx`: base and head side by side, each function's cyclomatic paired across the sides), Diff and Tests. `tests-screen.tsx` is the Tests screen: All / For the selected node (`testsAlongside`, `src/core/tests-alongside.ts`, which the inspector's Tests tab uses too), the counts (`testCounts`), the files' trees and the changed nodes, each going to Structure. `view.ts` holds the graph frame's zoom and pan rules (fit, zoom, pan, pin, centre, resize, all clamped), pure and tested in node. The CLI reads that file, never vite, so it must be built first: `pnpm build`, `pnpm review` and the tests' global setup (`vitest.setup.ts`) all build it.
- `src/test-support/` builds temporary git repos, Cargo workspaces and a fake `gh` for the tests. Pipeline rules are tested on `readStacks` with `fakeReader`/`fakeLinker` (`fakes.ts`); only what needs a real reader goes through `readRange` with the real adapters (`read-range.ts` there). `src/fixtures/` holds captured `cargo metadata` and depcruise output.
- `plugin/` is the Claude Code plugin (`plugin/skills/visual-review/SKILL.md` writes notes onto a page), and `.claude-plugin/marketplace.json` makes the repo its marketplace (`pablocm90`). The skill runs the CLI through npx at the version `package.json` says (`plugin.test.ts` keeps `plugin.json` and the pin in step); `VISUAL_REVIEW_PACKAGE` swaps in another npm spec, such as a packed tarball's absolute path.

## Commands

- `pnpm install`, then `pnpm check` (biome), `pnpm typecheck` (tsc 7, no emit), `pnpm test` (vitest, ~30 s), `pnpm mutate` (Stryker), `pnpm build` (`dist/`: the CLI as JS via `tsconfig.build.json`, plus the page).
- The package is `@pablocm90/visual-review` with the bin `visual-review` (`dist/cli.js`), shipping only `dist/`. Anything the CLI imports at runtime must be in `dependencies`; what only the page bundles (React, ELK, highlight.js) stays in `devDependencies`. Check an install with `pnpm pack` and `pnpm add <tarball>` in a scratch project.
- **Pre-push gate:** `pnpm check && pnpm typecheck`. CI (`.github/workflows/ci.yml`, GitHub Actions on every push) runs those plus `pnpm test` and `pnpm build`, with git and cargo on the runner.
- `src/index.ts` is the package entry: types only (`Reader`, `Graph`…). Node ids are part of a reader's contract (JSDoc on `GraphNode`): notes are keyed by them.
- cargo runs inside the reviewed checkout (its `.cargo/config.toml` must apply) but with `RUSTUP_TOOLCHAIN` set to what rustup picks outside it, so the checkout's `rust-toolchain.toml` can't choose cargo.

## Stack and gotchas

- Node 22.22 (`.tool-versions`) runs the `.ts` sources directly by type stripping: relative imports carry `.ts`, and no syntax that needs emit (enums, parameter properties).
- TypeScript strict with `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` and `noPropertyAccessFromIndexSignature`: index results are `T | undefined`, and `process.env['X']` takes brackets.
- Biome: single quotes, width 100, arrow parens as needed; two a11y rules are off under `src/viewer/**`.
- TypeScript 7 has no JS compiler API, so dependency-cruiser parses TS through `@swc/core`. Without it the web graph silently reads no modules.
- The tests shell out to real `git` and `cargo`. The viewer's first-page tests can flake against a cold ELK under load (1 s `findBy`); ask before raising the timeout.

## Conventions

- **This repo will be public.** Commit messages and PR bodies carry no `Claude-Session:` line, whatever the attribution reminder says. Keep `Co-Authored-By`.
- Changes land through PRs from a task branch (`claude-dev task <slug>`), never pushed straight to `main`.
- Publishing to npm and flipping the repo public are outward-facing steps the user runs or approves.
