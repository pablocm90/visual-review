# visual-review

Structural review pages for pull requests, ranges and uncommitted work: the Rust crates and modules, the TS/JS modules and the Rails classes of a repo, before and after, with what changed coloured, and optional notes written by Claude or anyone else. Being made public as `@pablocm90/visual-review`.

## Where things are

The layout: `src/core/` holds the ports (`Reader`, `Linker`), config, `read-range.ts` and `read-stacks.ts`, the diff, the collapse rules (`visible-diff.ts`: what is drawn at an expansion, its unchanged edges merged per pair of boxes unless the page's "All edges" is ticked, what the page's Show keeps of it, `changesOnly` (the default: changed nodes and the ends of added or removed edges) or `nearChanges` (one hop of any edge touching a change), or, on a PR's later round, `sinceLastReview` (what changed since its last review, at the expansion drawn), and what going to an id opens, widening Show as far as it needs) and notes, placed on them (`notes.ts`); the adapters sit behind the ports in `src/readers/{rust,typescript,rails}/` and `src/linkers/fetch-axum/`, listed in `src/adapters.ts`, which `cli.ts` hands to `readRange` (the core imports neither it nor `on-path.ts`); `src/git/` holds the git, `gh` and `PATH` plumbing; `src/viewer/` is the page, which imports the core and never the reverse. Bare file names below live in those folders.

- `src/cli.ts` is the entry point (`pnpm review <pr | from..to>`, or nothing for uncommitted work). `read-range.ts` checks out both sides of a range and reads each with `readStacks` (`read-stacks.ts`) through the readers in `src/readers/` (Rust: `crate-graph.ts`, `crate-modules.ts`, `rust-tests.ts`, `rust-measure.ts`; TS: `web-graph.ts` via dependency-cruiser, `typescript-tests.ts`, `typescript-measure.ts`; Rails: `rails-graph.ts`, `ruby-tests.ts`, `ruby-measure.ts`, parsing with tree-sitter-ruby in `ruby-syntax.ts`, no Ruby run), each implementing `Reader` (`reader.ts`): `roots` lists candidate roots, `holds` says whether one is its stack given that stack's settings, `graph` reads one stack under its drawn id, and it owns its test files, read only under a drawn root. `readStacks` owns the policy: naming, added and dropped stacks, labels, skips, linker stacks and edges with an undrawn end. It names roots in one pass, reader order then root order: a root's name (its own, else its directory, else the repo folder at `.`) gives a tentative id, the first free `~N` (`web~2`) when taken, and `holds` is asked with that id's settings; only a root that holds takes the id. A TS root is any directory with a `package.json` whose source root (tsconfig `rootDir`, else its one `include` folder, else `src/`) holds TS/JS sources, `node_modules` skipped; its stack id is the directory, or the package.json name (else the repo folder name) at the checkout root. A bare import of a sibling package's name joins the file to that stack, since checkouts have no `node_modules`. A Rails root is any folder with `config/application.rb` outside `vendor/`, `node_modules/`, `test/` and `spec/`, named by its directory, or the repo folder name at the checkout root; its boxes are the `app/` folders holding Ruby (`app/lib` as `app/lib`) plus `lib/`, or the deepest folder matching a config box glob (`app/models/*` gives `models/billing`; a box doesn't change a class's constant), and its nodes are classes keyed by constant (`<stack>/class/Admin::UsersController`), read from the file's `class`/`module` definition naming the longest tail of its path. Its edges are the constants a class writes, resolved through Ruby's lexical scope, and its model associations, resolved from the owner's constant as ActiveRecord does (`class_name:`, `source_type:`, `source:`, else the name, singularized for `has_many`, matched ignoring case). Its test files are `*_test.rb` under a `test/` folder and `*_spec.rb` under a `spec/` folder, read by one walker (`ruby-tests.ts`): `test "…"` calls and `test_` methods under a heading per class constant, and `it` / `specify` / `example` / `scenario` (an `it { … }` named by its block) and `it_behaves_like` (named by its arguments) under a heading per `describe` / `context` / `feature`, named as RSpec names groups; a test word on a receiver is no test, and shared and `x`/`f` groups aren't read. `config.ts` validates `visual-review.config.json` (Zod, `strictObject`), read from the head revision or else the working tree, and applies to both sides: readers get a stack's settings in `holds` and `graph` (box globs, `sourceRoot`), stacks added with `reader`+`root` keep their key as id, relabelling happens in `readStacks` on drawn ids, and a dropped (`false`) stack's graph is never read. A reader may name the command its `graph` runs (`Reader.tool`, `cargo` for Rust): when it isn't on `PATH` (`on-path.ts`, a lookup, nothing run), none of its stacks is read and the review lists its kept stacks as `skipped` (`skipped.ts`), shown on stderr and as the alert atop the page's findings rail; its test files are still read. The CLI looks up `git`, and `gh` for a PR number, the same way and exits 1 naming the one missing, and refuses a root with no `.git` entry (`repoRoot`). What it and serve write under `.reviews/` goes through `writeAnew` (`src/write-anew.ts`): a temporary file renamed over the path, so a link there is replaced, overlapping writers all succeed, and a regular file's mode is kept. It finds the repo root under `safe.bareRepository=explicit`, so a folder a branch lays out as a bare repository is never taken for the repo, and every later git call runs from that root. Each `Reader` names itself and the stack fields it takes (`stackFields`). Naming problems (an added root detected as another stack, an added key detected elsewhere or drawn by another reader) fail before any graph is read; the rest (undetected, field not taken, unlinkable: `checkConfig`) once both sides are read. `pnpm build` writes `dist/config.schema.json`, `dist/notes.schema.json` and `dist/review.schema.json` from their Zod schemas (`write-schemas.ts`). Linkers (`Linker`, `linker.ts`) then draw edges across stacks from the drawn nodes: `linkers/fetch-axum/linker.ts` reads the fetch calls of every TS stack's files and the `.route("…")` paths in the module files (the files its targets reach, not `tests/` or nested crates) of every crate whose `Cargo.toml` depends on axum (`api-paths.ts` parses both), and lists unrouted calls as dangling; with no axum crate it draws nothing. The config's `linkers` entry turns one off or names its `from`/`to` stacks. `test-changes.ts` compares a test file's tests across the sides, tests of one name paired in order, and `anchoredTests` gives each its trail, counted from the second of one trail in the file; each test file carries its stack's id (`stack`, from the deepest root of its reader holding it), since every reader draws its stack node at path `''`, which holds no path. `diff-graphs.ts` diffs the sides, matching edges by `edgeId` (`graph.ts`, the `<from> -> <to>` notes use too). `visible-diff.ts` draws a node inside closed boxes as the outermost of them, at any depth. `notes.ts` parses notes, places them at an expansion (an edge's note moves onto the edge drawn in its place) and lists their problems; notes also take `answers`, by the last review's anchors as `<kind> <id>` (`anchorKey`), and `unasked`, by node or edge id, refused on a page with no `sinceReview`. For a PR number `cli.ts` asks `lastReviewOf` (`src/git/last-review.ts`) for the newest `.reviews/*.review.json` of that PR at another head, read through `pastReviewOf` (`review.ts`), which needs only `verdict` and `reviewed` and keeps what it can of `body`, `read` and `comments`, comment by comment, so an older format's review still counts, and `lastReviewOf` adds `calledFine`, the findings whose newest answer over all the PR's reviews is `fine`; a file git tracks came with the repo, so neither it nor pruning counts it (`git ls-files --others`, run from the repo root: inside `.reviews/` a branch could lay out a bare repository git would use, whose config runs commands), the head must be a full SHA, and it's compared with the new head as a commit, so a tag object of that head is that head; `readRange` reads that head as a side of its own, the reading's `reviewed`, with the PR's own diff at that head as `pullRequest` (from `merge-base(from, head)`, reusing the range's base graph when that's the same commit, else one more side) (or `gone` when the commit doesn't resolve, a force-pushed head still in local objects still reading, or `unreadable` with the message when reading it fails, which doesn't stop the review), and `sinceReviewOf` (`since-review.ts`) diffs it against the head, counting only paths the PR changes at either head and keeping only the nodes and edges it changes at either, so a merge of `main` counts only where it touches one of its paths: `PageData.sinceReview`, with `changed` Show's Since last review (`sinceLastReview`; a part the PR has restored stays in `nodes` or `edges`, drawn as unchanged, its edge kept apart from the merge like a noted one while this choice is picked, a reviewed id going by the head's name when renamed since, and what the head doesn't hold goes in `dropped`, named by a line under Show), and without it a header line saying the full review is shown. `changed` also lists `symbols`, `decisions` and `tests`, by the ids their comments anchor to, and `files`: the reading holds each pair's symbols and tests too, a symbol or test kept when the PR changes it at the head or, by its former id, at the reviewed head; the page marks them "changed since" on any later round, whatever Show holds, through `ChangedSinceMarks` (`changed-since.tsx`), a context read by the symbol rows, logic lines, test lines and `Patch`, a diff line counting by its file. `sinceReview`'s every variant also carries the last review's `verdict`, `body`, `calledFine` and `comments`, each given by `previous-comments.ts` its `target` at the head and, when compared, `changedSince`, the commits touching its file (the reading's `commits`, one `git log -z` of `reviewed..to`), absent for "As it was"; the compared variant adds `changedWithoutComment` and `stillRead`, the start `storedReadMarks` takes when nothing is stored for the range. On the page `LastReview` (`last-review.tsx`) lists them atop the left column, and `SaidBefore` (`said-before.tsx`, context `LastSaidOnPage`) shows one under its anchor: Note panel (an edge's also on the arrow drawn in its place, `edgesSaidInPlace`), symbol rows, logic lines, test lines, patch rows, the rail's findings, not the Look first band, which leaves out what's `calledFine`. `Said`, which both render, shows Claude's answer under its comment, by the anchor as said; `LastReview` also lists the notes' `unasked`. `pruneReviews` keeps each PR's newest review past its page. `read-range.ts` also counts each side's churn per drawn file (`git log` over `metrics.churnDays` days before that side's committer date; uncommitted work's head counts up to `HEAD`), and `metrics.ts` puts it on the changed nodes plus one hop of the diff's edges, with fan-in/out and, from the reader's optional `measure` (Rust: `rust-measure.ts`; TS: `typescript-measure.ts` over Babel's AST; Rails: `ruby-measure.ts` over tree-sitter-ruby; TS and Rails test files measured as `undefined`, which leaves a file unmeasured), lines, functions, cyclomatic (its highest, its total and each function's, `cyclomatic.byFunction`, a Rust function's `?`s counted apart as its `earlyReturns`) and ABC; a box takes the highest of each measured inside it (`highestInside`). For each changed file `read-range.ts` also reads both sides' symbols through the reader's optional `symbols` (TS: `typescript-symbols.ts`, over the Babel parse and walk it shares with `typescript-measure.ts` in `typescript-syntax.ts`; test files and non-script files read none, and a parse error is kept as `unreadable`; each function's and method's decisions, its guards, ifs, ternaries, loops, cases, outermost logicals, catches, returns inside a branch and throws, are read by `typescript-decisions.ts` as normalised source text with their depth and line; Rails: `ruby-symbols.ts`, over tree-sitter-ruby, test files reading none and a parse error or a file over the limit in `too-big.ts` kept as `unreadable`: a class or module by its full constant, its methods, setters, attrs, delegates and scopes under it, visibility walked in order per body, and what a class holds cut from its hashes as holes, an attr or delegate call only when its symbols read all of it, so an edit inside reads there alone; it reads no decisions yet), lists as `symbolsNotRead` the stacks with changed files whose reader has none, and `symbol-changes.ts` pairs the symbols across the sides (scope, name and kind, a method and an accessor pairing across those two kinds when neither has an exact partner; formatting by text hash; renames by body hash, or "probably" by token similarity; moves between changed files), diffs the export names, gives the file its kind of change, `api`, `logic` or `formatting`, and gives an edited or renamed function whose decisions differ its `logic` lines (`logic-diff.ts`: an LCS over kind and text keeps the same ones, and inside each gap base and head decisions of one kind pair in order as changed, the rest removed or added), and across all the files a removed line whose kind and text another symbol gained (a new symbol's decisions, or an edited one's added lines; a symbol moved whole gains nothing) becomes `moved`, with `movedTo` (`movedToNode` when in another file), each gain taking one line; `symbol-findings.ts` raises the `api` findings and the `logic` ones, each `<prefix>:<symbol id>`, the id `anchoredSymbols` counts, so a getter and setter of one name are told apart and a rename goes by its new name (a guard or catch removed needs a look, a function's other decision changes, a moved guard among them, are one finding for information), and `findings.ts` adds `tests:untested-logic` for a file with a logic finding and no changed test alongside it. `split-suggestion.ts` groups the reading order's parts by the diff's edges running directly between them, in any state, so no unchanged node, box or stack joins two; when two groups reach `metrics.splitParts`, `findings.ts` raises `cohesion:split`, for information, with no target and each group's ids in `groups`, which the rail draws as a button each, named by the first part's path (or label, for a stack). `PageData` carries them as `symbols`, and `parsers`, the parser packages' versions, read by `cli.ts`. `metric-findings.ts` marks the head side's leaves over the config's thresholds, `look` or `info`, for the Metrics cells, and `findings.ts` (its words in `GLOSSARY.md`) raises the page's findings from them and from the skipped, undrawn and dangling facts as `PageData.findings`, each with a dimension and a level; the page adds the notes' flags (`findingsOf`), ranks Look first (`lookFirst`) and places findings on what is drawn (`findingsAt`), as notes are. `reading-order.ts` orders the parts (changed nodes with no changed node inside) by the head graph's edges, depended-upon first, a part reaching through its boxes' edges too; parts that reach each other are one cycle, read in id order, and removed parts come last: `PageData.readingOrder`, listed atop the left column (`reading-order-list.tsx`) with the files outside the graph after it, and numbered on the drawn parts. On the page `J`/`K` walk the parts (a document key listener in `review-page.tsx`, on while Structure is shown, any case, ignored in textareas and with Ctrl, Meta or Alt) and `A` marks the selected part read; the marks are kept in `localStorage` by range (`read-marks.ts`, Zod-parsed, every access in a try), so they last a reload but not a new serve, whose port, and so origin, is new; the review sends those on the reading order's parts, and the review tray counts them. The Metrics tab reads the page data through `metric-totals.ts` (its tiles), `metric-rows.ts` (its measured leaves and their sort) and `hotspot-moves.ts` (its chart's base → head points and who enters the corner). `page.ts` is the page's contract: it builds the page data from a range reading (every field present, stamped with the CLI's version), puts data and notes into `viewer.html`'s slots and reads them back (`main.tsx` reads them through it, so it imports nothing from `node:`), and on `--notes` checks the notes against the data inside the page and refuses a page another version wrote. The CLI only does I/O around it; the `.json` beside the page is for readers such as the skill. `pnpm review serve [--no-open] <page.html>` (`src/serve.ts`) serves a written page, opening it unless `--no-open`: node:http on `127.0.0.1` port 0, the page at `/<token>` (a random token per serve, filled into the page's `review-serve` slot by `page.ts`'s `servedPageHtml`), the review POSTed to `/<token>/review`, any other path or `Host` 403. A body `parseReview` (`src/core/review.ts`, Zod, `dist/review.schema.json`: a `verdict`, `approve` | `comment` | `request-changes`, an optional general comment `body`, `reviewed`, the range and PR number the page was drawn for, `read`, the reading order's parts marked read, and `comments`, one per anchor: a comment on a part or edge, or an answer to a finding by its id) accepts is written as `<name>.review.json`, answered 204, its path printed, and serve exits 0; one it refuses gets 400 with the parse error and serve keeps serving. `main.tsx` reads the token through `pageIn` and hands `ReviewPage` a `send` that POSTs with `sendReview` (`page.ts`, which the serve tests call too, so they send what the page sends); with no token there's no `send`, and the page shows no comment field and no review tray (`review-tray.tsx`, a bar at the page's foot: closed, it counts the drafts by kind; open, it lists them, comments in reading order, then finding answers by their finding's title, each going to its anchor (a diff line's at its row, on the Diff tab or, when no node holds its file, in the files outside the graph) or the finding's target, and the parts read with nothing to say, and holds the general comment, the verdict, suggested from the drafts until one is picked, Send, and What Claude gets, the review as lines). `main.tsx` also pings `/<token>/ping` (`pingServe`) on load and every 30 s; serve waits for the first ping up to 24 h (`VISUAL_REVIEW_FIRST_PING_MS`), then each ping refreshes its idle timer (10 min, `VISUAL_REVIEW_IDLE_MS`); when either ends, serve exits 1 with "No review sent". Serve's lock, `~/.cache/visual-review/serve/<sha256 of the page's real path>.json` (`{ pid, port, token }`, mode 600, Zod-checked), outside the repo so that no checked-out file can be taken for it (a umask of 077 checks every file out as mode 600, so no mode can tell them apart), makes a second serve of a live page open its URL (print it on stderr under `--no-open`) and exit 0 with nothing on stdout; a lock whose server doesn't answer `POST /<token>/alive` (a check apart from the page's ping, so it never starts the idle count), or that doesn't parse, is replaced, and serve removes its own on exit, on a signal too. A home that isn't absolute, or a lock it can't write, exits 1 naming the lock.
- A lockfile changed in the range becomes `PageData.dependencyChanges`, read by `readLockfiles` (`read-lockfiles.ts`, a `readRange` option beside `Adapters`, since `readStacks` never uses them) through each `Lockfile` port (`lockfile.ts`) in `src/lockfiles/{pnpm,npm,yarn,cargo,bundler}.ts`, listed in `adapters.ts`; they aren't `Reader` methods because a lockfile needs no drawn stack, a gem no Rails root. `git show` reads each side's text at its commit, so a symlink reads as its link text, and `\r\n` is normalised once there. Lockfiles of one ecosystem in one folder that changed together are read as one, so moving package manager raises only what moved, and a rename goes by its last path. A reader fails closed: any line its tool wouldn't have written throws, which raises "not read" naming only the format, since a quieter reading could hide a package. `yarn.lock` alone takes `Lockfile.manifest`, each side's `package.json` files under its folder. `packageChanges` (`dependency-changes.ts`) pairs the sides by compatibility line, and `dependency-findings.ts` raises the findings, each with `Finding.file`, which the rail, Look first and the tray open through `showFile` in `review-page.tsx`: the node holding the file on its Diff tab, else the files outside the graph, landing at the patch's top.
- `src/viewer/` is the page: React + ELK, built by vite with `vite-plugin-singlefile` into one file, `dist/viewer.html`. `review-page.tsx` holds the tabs (Structure and Tests shown so far, picked by the URL's hash; the selection is its state, so it holds across tabs) and the Structure screen: the findings rail on the left (`findings-rail.tsx`: skipped stacks, then the findings grouped by dimension, each going to its target or opening the changed files outside the graph), the triage strip (a chip per dimension, filtering the rail and Look first and dimming other badges) and the Look first band above the graph, one findings badge per drawn node or edge, the graph, coloured by change, churn, complexity or kind of change (`colour-by.tsx`; a box takes the strongest kind inside it, a changed node with none reads "symbols not read"), and the inspector on the right, its tabs Note, Metrics (`metrics-tab.tsx`: base and head side by side, each function's cyclomatic paired across the sides), Diff (on a served page a numbered patch line takes a comment through `CommentOn`, here and in the files outside the graph, anchored by `lineAnchor`, its place read back by `placeOfLine`; a patch opens by itself when it holds a draft or the landing, the row `useLanding` keeps until the selection or the panel changes), Tests and Symbols (`symbols-tab.tsx`: a file's symbols grouped by change, an edited function's logic lines under it, or a box's files with theirs; a logic line that changed opens the Diff tab on its file's patch, at its row by the line numbers `highlightPatch` reads from the hunk headers, else at the patch's top; on a served page a symbol row and a logic line each take a comment through `CommentOn`, a logic line's anchor from `decisionsOf` in `symbol-findings.ts`, which its `logic:removed` finding's id comes from too). `tests-screen.tsx` is the Tests screen: All / For the selected node (`testsAlongside`, `src/core/tests-alongside.ts`, which the inspector's Tests tab uses too), the counts (`testCounts`), the files' trees (`TestFiles`, which the inspector's Tests tab uses too; on a served page each test takes a comment, its id the file and heading trail, counted from the second of one trail, whose draft in the tray goes to, and counts on, the node `nodeOfTests` names, the one whose Tests tab shows the file) and the changed nodes, each going to Structure. `view.ts` holds the graph frame's zoom and pan rules (fit, zoom, pan, pin, centre, resize, all clamped), pure and tested in node. The CLI reads that file, never vite, so it must be built first: `pnpm build`, `pnpm review` and the tests' global setup (`vitest.setup.ts`) all build it.
- `src/test-support/` builds temporary git repos, Cargo workspaces and a fake `gh` for the tests. Pipeline rules are tested on `readStacks` with `fakeReader`/`fakeLinker` (`fakes.ts`); only what needs a real reader goes through `readRange` with the real adapters (`read-range.ts` there). `src/fixtures/` holds captured `cargo metadata` and depcruise output.
- `plugin/` is the Claude Code plugin (`plugin/skills/visual-review/SKILL.md` writes notes onto a page, on a later round with its answers to the last review, serves it in the background and acts on the review's verdict when `serve` exits), and `.claude-plugin/marketplace.json` makes the repo its marketplace (`pablocm90`). The skill runs the CLI through npx at the version `package.json` says (`plugin.test.ts` keeps `plugin.json` and the pin in step); `VISUAL_REVIEW_PACKAGE` swaps in another npm spec, such as a packed tarball's absolute path.

## Commands

- `pnpm install`, then `pnpm check` (biome), `pnpm typecheck` (tsc 7, no emit), `pnpm test` (vitest, ~40 s), `pnpm mutate` (Stryker), `pnpm build` (`dist/`: the CLI as JS via `tsconfig.build.json`, plus the page).
- The package is `@pablocm90/visual-review` with the bin `visual-review` (`dist/cli.js`), shipping only `dist/`. Anything the CLI imports at runtime must be in `dependencies`; what only the page bundles (React, ELK, highlight.js) stays in `devDependencies`. Check an install with `pnpm pack` and `pnpm add <tarball>` in a scratch project.
- **Pre-push gate:** `pnpm check && pnpm typecheck`. CI (`.github/workflows/ci.yml`, GitHub Actions on every push) runs those plus `pnpm test` and `pnpm build`, with git and cargo on the runner.
- `src/index.ts` is the package entry: types only (`Reader`, `Graph`…). Node ids are part of a reader's contract (JSDoc on `GraphNode`): notes are keyed by them.
- cargo runs inside the reviewed checkout (its `.cargo/config.toml` must apply) but with `RUSTUP_TOOLCHAIN` set to what rustup picks outside it, so the checkout's `rust-toolchain.toml` can't choose cargo.

## Stack and gotchas

- Node 22.22 (`.tool-versions`) runs the `.ts` sources directly by type stripping: relative imports carry `.ts`, and no syntax that needs emit (enums, parameter properties).
- TypeScript strict with `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` and `noPropertyAccessFromIndexSignature`: index results are `T | undefined`, and `process.env['X']` takes brackets.
- Biome: single quotes, width 100, arrow parens as needed; two a11y rules are off under `src/viewer/**`.
- TypeScript 7 has no JS compiler API, so dependency-cruiser parses TS through `@swc/core`. Without it the web graph silently reads no modules.
- The tests shell out to real `git` and `cargo`. `review-page.test.tsx` lays its fixture out once at load and waits up to 3 s (`asyncUtilTimeout`) in every `findBy` and `waitFor`, so a loaded machine renders the first page in time; ask before raising a timeout, and diagnose a flake with the test file run 12× in parallel under busy loops before blaming load. `vitest.config.ts` runs the `.test.ts` files first and the `.test.tsx` files after them, one at a time (`sequence.groupOrder`, `fileParallelism`), because a page test's slowdown follows the other files running during it: keep them apart. To expose a page test that reads before a relayout lands, delay `layoutDiff` by a temporary `setTimeout` and run the file at several delays; it should stay green.

## Conventions

- The domain's words (finding, dimension, level, fact, Look first) are defined in `GLOSSARY.md`.
- **This repo will be public.** Commit messages and PR bodies carry no `Claude-Session:` line, whatever the attribution reminder says. Keep `Co-Authored-By`.
- Changes land through PRs from a task branch (`claude-dev task <slug>`), never pushed straight to `main`.
- Publishing to npm and flipping the repo public are outward-facing steps the user runs or approves.
